# Phase 6 security hardening

This phase adds defense in depth without changing application features.

| Protection | Threat | Mitigation | Trade-off |
| --- | --- | --- | --- |
| CSRF | A hostile page causes a signed-in browser to mutate data. | Every unsafe `/api` request requires `X-CSRF-Protection: 1`. Browser requests must also pass the exact CORS origin allowlist. The custom header forces a preflight for cross-origin JavaScript and cannot be added by a plain HTML form. | Non-browser clients must add the marker header. This is an origin-bound marker design, not a rotating token, so XSS remains a separate threat. |
| Credentialed CORS | Session cookies or responses are shared with an unintended web origin. | Credentials are enabled only for exact `ALLOWED_ORIGINS` values. Allowed methods and headers are explicit; denied origins fail closed. | Each trusted frontend origin must be configured, and production origins must use HTTPS. |
| Authentication rate limits | Attackers guess passwords or flood registration/reset endpoints. | Login/registration and reset endpoints have separate IP budgets and standard rate-limit response headers. Limits are environment-configurable. | Shared networks can exhaust a budget; operators can tune limits without code changes. |
| Secure headers | Framing, MIME sniffing, referrer leakage, and permissive browser defaults. | Helmet is enabled with same-origin resource policy and `no-referrer`; Express identity is disabled. | Frontend CSP belongs at the frontend host. Same-origin media hosting is expected. |
| Input validation | Oversized, ambiguous, unexpected, or operator-shaped values reach application/database logic. | Security-facing Zod schemas are strict, query parsing is simple, JSON/form payloads are bounded, identifiers are validated before lookup, and recursive input safety rejects Mongo operator keys, dotted paths, prototype keys, and excessive nesting. | Unknown security fields and oversized backups are rejected. The JSON ceiling remains 10 MB to support valid backup restores. |
| Production errors | Stack traces, database details, or secrets leak through failures. | Unexpected 5xx responses use a fixed message and request ID; details and stacks remain server-side. Expected 4xx messages remain actionable. | Production clients use the request ID rather than receiving debugging internals. |
| Environment secrets | Placeholder secrets or unsafe origins reach production. | Startup validates secret length/non-placeholder values, TTL/rate/lock ranges, exact origins, and HTTPS production origins. Reset tokens cannot be exposed in production. | Invalid deployments refuse to start. Root bootstrap secrets must be removed after provisioning and trigger a warning if retained. |
| Session cookies | Cookies are read by scripts, sent cross-site, or accepted over plaintext. | Cookies are HttpOnly, SameSite=Lax, Secure in production, host-only, rolling, TTL-bounded, and use the `__Host-` prefix in production behind a trusted proxy. | Production requires HTTPS and correct proxy forwarding. |
| Lock and suspension | Repeated guessing succeeds or suspended users retain sessions. | Five failed password attempts cause a timed lock by default. Successful login/reset clears it. Suspended/disabled accounts receive a session-version increment and registered sessions are removed; middleware rejects them on their next request. | Attackers can temporarily lock a known account. Responses stay generic to limit account enumeration. |
| Audit logging | Security-sensitive actions cannot be reconstructed. | Authentication successes/failures/lockouts, password/session changes, and administrative role/status changes are recorded with bounded IP/user-agent metadata. CSRF rejection is structured in the server log to avoid an unauthenticated database-write flood. | Adds audit volume. Passwords, tokens, cookies, and request bodies are never recorded. |
